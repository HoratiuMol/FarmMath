## 🐄 Gameplay Roadmap — Farm-Sim Feature Options (proposed 2026-08-12, planning only — nothing below is implemented)

Founder asked specifically about **animals unlocked via harvested crops, more crop types, and feeding animals**, plus a broader menu of options common to this genre (Stardew Valley / Hay Day / FarmVille-style loops). Laid out here as a planning menu, not a commitment — each item names what it would touch so a future session can scope it properly. The decorative wandering cow that already exists is purely cosmetic (no gameplay effect) and would become the *first* real animal if the "animals" track below is picked up.

### A. More crop types (extends the existing single-crop wheat loop)
- **Second/third crops** (corn already flagged in the Not-Done list as a v1.0 item, plus e.g. carrots/pumpkins): each crop would need its own growth duration, currency value, and a distinct procedural tile look (reusing `drawWheatTile`'s phase-layered pattern approach). Math-difficulty tie-in idea: unlock later crops as a *reward* for exercise streaks/accuracy, giving the math side a visible payoff beyond extra fields.
- **Crop variety as a currency sink**, not just a time sink — different crops selling for different amounts opens up simple "which crop is worth planting right now" decisions without needing a real market/pricing system.
- **Crop quality tiers** (e.g. a bonus-value "golden" harvest chance tied to solving a bonus math problem at harvest time) — reuses the existing math-exercise plumbing (`openExerciseForTimeReduction` is a precedent for "exercise modifies an in-progress cell").

### B. Animals unlocked via harvested crops
- **Unlock condition**: gate each animal behind a cumulative harvest count of a specific crop (`fieldsCompletedTotal` already tracked on `PlayerEntity`, or a new per-crop counter) — e.g. "harvest 20 wheat to unlock chickens," matching the founder's framing directly.
- **Placement**: animals would need their own placeable-object model, most naturally as a new `OccupantType` (or a parallel "decoration/animal" layer independent of `cells`, similar to how the current decorative cow is a free-floating position outside the `cells` model entirely) with its own small 3D/Canvas asset per species, following the barn/fence pattern (parsed mesh or hand-drawn procedural shape, founder's choice per animal).
- **Behavior**: the current cow's wander/graze coroutine plus its new barn-rectangle collision-avoidance are a directly reusable base for any additional wandering animal — the obstacle-avoidance approach would need to generalize from "one hardcoded barn rectangle" to "avoid every solid object" (barn, other animals, maybe fences/paths) if multiple animals are added, which is a real design decision, not just more code (see the "physics" note under Known Gaps below).
- **Progression shape**: a small unlock ladder (chickens → cow → sheep → pig, or similar) gives the harvest loop a visible sense of growth beyond "number goes up," and dovetails with a Barn/Building upgrade track (see D).

### C. Feeding animals
- **Core loop idea**: harvested crops become animal feed instead of (or in addition to) pure currency — e.g. wheat feeds chickens, corn feeds pigs — turning "what do I plant" into a real resource-allocation decision instead of a single optimal crop.
- **Needs a hunger/care state per animal**: a simple depleting timer (mirrors `GrowthCalculator`'s timestamp-based approach, so it also survives app kill/background for free) that the player tops up by feeding; a hungry-too-long animal could pause producing rewards rather than punishing harshly, keeping this friendly for the target 6-12 audience (no death/loss mechanics).
- **Payoff for feeding**: animal products (eggs/milk/wool) as a second reward currency, or animals boosting nearby crop growth speed as a "farm synergy" mechanic — either gives feeding a clear reason to matter instead of being busywork.

### D. Other options common to this genre (not specifically requested, offered as context)
- **Animal products / a second currency** — eggs, milk, wool sellable separately from wheat currency, mentioned above under C.
- **Barn/building upgrades** — larger barn capacity (more animals), cosmetic barn skins, unlocked via the same harvest-count-gate idea as animals; the new "move barn" feature this session is a natural stepping stone toward "the barn is a real upgradeable object," not just fixed scenery.
- **Decorations/cosmetics** — flowers, fences styles (the fence mesh already supports a picked color palette per the fence-preview options), placeable scenery bought with currency — a low-risk way to add "personal expression" without touching core math/growth systems.
- **Seasons/weather** — cosmetic ground/sky palette swap on a timer, optionally affecting growth speed; bigger lift than it sounds since every tile-color constant in `FarmGridCanvas` is currently hardcoded.
- **Quests/daily goals** — "harvest 5 wheat and solve 3 problems today" style short-term objectives, reusing the existing daily-reset midnight boundary (`checkAndApplyDailyReset`) as the natural reset point.
- **Achievements/milestones** — one-time badges off existing counters (`fieldsCompletedTotal`, `currentStreak`, `exercisesSolvedToday`) — cheapest item on this whole list since no new tracking is needed, only new UI + one-time-fired flags.
- **A real market/pricing screen** — if crop variety (A) ships, a simple sell screen with per-crop prices (possibly fluctuating) turns "harvest = instant flat currency" into a small economic decision.
- **Friends/visiting farms** — explicitly out of scope per the BRD's offline/no-backend/no-network constraint (NFR-002/NFR-008, reconfirmed this session's context) — flagged here only so it's clearly *not* silently on the table.

## 3D Engine Options (comparison)

The barn mesh work proved the current approach can render real 3D geometry, but it's worth being explicit about the tradeoff being made by staying Canvas-only versus adopting an actual 3D pipeline, in case the founder wants to revisit this as more 3D assets get added.

- **Current approach — Jetpack Compose Canvas + hand-written OBJ parsing/projection (`BarnMesh.kt`).** Zero new dependencies, stays 100% inside the existing Kotlin/Compose codebase and skillset, smallest APK footprint, and — since geometry is precomputed once and cached — cheap per-frame. The ceiling is low, though: every new 3D asset needs its own bespoke parse-and-project code (no shared scene graph), there's no runtime lighting/camera movement (the "camera" is a fixed baked-in rotation), no animation support, and no depth-buffer — the painter's-algorithm sort that works for one convex-ish barn will get harder to keep correct as more overlapping 3D objects are added to the same scene. Good for "a small number of static hero props," bad for "many independently-posed/animated 3D objects."
- **Filament (Google's real-time PBR renderer) or SceneView (a Kotlin/Compose wrapper around Filament + ARCore).** The most natural upgrade path if more real-time 3D is wanted: stays fully native/Kotlin, no language switch, integrates into a `GLSurfaceView`/Compose `AndroidView` embed, supports glTF (and OBJ via conversion) with proper depth buffering, real lighting/shadows, and camera control out of the box. SceneView specifically gives a declarative Compose-friendly API for dropping 3D models into a scene. Cost: a real new dependency and rendering surface to manage, some learning curve, and glTF is the preferred format (this project's assets are OBJ and would need conversion, e.g. via Blender, which isn't available in this environment today).
- **Godot (open source, GDScript or C#).** A genuine game engine with a proper 3D scene graph, physics, animation, and good mobile/Android export support out of the box; free and lighter-weight than Unity. Cost: full architecture rewrite — the existing Kotlin/Compose/Room codebase would not carry over, and the team would be picking up a new engine and (likely) GDScript.
- **Unity.** The option this project explicitly moved away from at kickoff (see the "Initial MVP scaffold" log entry) specifically because the founder wanted a literal Android Studio/Kotlin project. Still the most asset-rich, best-tooled option for true 3D low-poly art with animation, and the easiest path to iOS later — but adopting it now means the same full rewrite cost as Godot, plus C# instead of Kotlin.
- **Raw OpenGL ES / Vulkan via the Android NDK.** Maximum control and performance, but means hand-building everything a game engine normally provides for free (scene graph, depth testing, lighting model, asset loading) — the highest implementation cost of any option here, rarely justified unless Filament/SceneView prove insufficient.

**Bottom line:** for "one or two more static hero props," the current Canvas approach is fine and keeps momentum. If the founder wants multiple animated/lit 3D objects, moving/rotating cameras, or a growing asset library, SceneView/Filament is the lowest-cost real upgrade (no rewrite, stays Kotlin); Godot or Unity are only worth it if the ambition shifts toward a full 3D game rather than a Canvas-rendered 2.5D one.
